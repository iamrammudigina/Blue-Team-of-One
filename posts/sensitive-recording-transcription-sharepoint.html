Transcribing sensitive recordings without letting them out

An investigations team asked a simple question: can we use Word's Transcribe on our interview recordings? The honest answer took three weeks of testing, because the real requirement was "transcripts, and the recordings never leave a controlled place." Here's the whole build — what each Microsoft 365 control actually blocked when I tested it, what none of them can block, and the surprises on the first real upload.

Ram Mudigina October 23, 2026 ~24 min read

The request arrived as a yes/no question about a feature. Those are the dangerous ones, because the feature usually works — Word will happily transcribe an MP4 — and the risk sits in where the file goes, who else can see it, and what happens to the text afterwards. Investigative interviews are about as confidential as content gets: statutory confidentiality, public-records exposure, and the possibility that a transcript ends up quoted in a formal proceeding.

So the work split into three questions, in this order. Which transcription engine keeps the recording somewhere the organisation controls? Which controls keep it there — and what does each one actually stop, as opposed to what the docs imply? And what breaks when real people start using it?

  • Engine: Stream on SharePoint, not Word Transcribe. Word saves the audio to the user's personal OneDrive and caps at 300 minutes a month; Stream keeps the transcript with the video, under the library's permissions and retention.
  • Controls: one site, one mail-enabled security group, owner-only sharing, Restricted Content Discovery, a Conditional Access "app enforced restrictions" policy plus a site-level BlockAccess, and an encrypting sensitivity label with no copy, print, export — or Copilot.
  • What testing showed: browser-only access still let a personal device edit transcripts, trim video and copy text. Microsoft has no per-device read-only video player. Blocking personal devices outright was the only site-scoped fix.
  • Detour: Defender for Cloud Apps blocked copy, paste and print perfectly — and can't be limited to one site, so it wasn't adopted.
  • Go-live: the first file was audio-only (no transcript), the second showed "No label" (MP4s are never auto-labelled), and the transcripts needed to go into another system that can't open labelled files.

01Word Transcribe or Stream? Read the storage line first

Both transcribe. The difference that matters for confidential content is where the audio lands and who controls it afterwards.

I compared the two strictly from Microsoft's documentation before building anything, and kept anything I couldn't source out of the client-facing answer.

The storage row decided it. A department's confidential recordings scattered across individual OneDrives is a records and access problem before it's a security one: nothing central to apply retention to, nothing central to audit, and access that walks out the door with each person.

Myth

Word Transcribe on the desktop runs under consumer terms because it's an "optional connected experience".

Reality

I said this in my first draft and had to correct it. Microsoft lists Transcribe under connected experiences that analyze your content — not the "optional connected experiences" category that falls under the Services Agreement. The real arguments against it are the OneDrive storage and the per-user cap.

Two quick checks belong at the start of any job like this. First, which cloud is the tenant in? Feature availability differs in GCC, and you can tell without admin rights:

# browser, no sign-in needed
https://login.microsoftonline.com/<domain>/.well-known/openid-configuration
# tenant_region_sub_scope = "GCC" -> GCC · missing -> commercial · login.microsoftonline.us -> GCC High
# also visible in Licenses: E3/E5 = commercial, G3/G5 = government

Second, is transcription already switched on everywhere? It almost certainly is — and that's worth telling the client on its own:

Connect-SPOService -Url "https://<tenant>-admin.sharepoint.com"   # Windows PowerShell 5.1, not 7
Get-SPOTenant | Select MediaTranscription, MediaTranscriptionAutomaticFeatures
# Enabled  Enabled   <- Microsoft's default
Get-SPOSite -Identity <site-url> -Detailed | Select *Transcri*
# MediaTranscription : Enabled   <- a per-site switch exists too

Every video in the tenant is already being transcribed

Automatic transcription is on by default, tenant-wide. Any video anyone has uploaded to SharePoint or OneDrive is being transcribed and its words made searchable to whoever can see the video. That's not a flaw in the new site — it's a pre-existing condition the client should know about, and it can be switched per site if they want it off elsewhere.

A throwaway site and public sample videos. Nothing confidential touches anything until the behaviour is known.

The unified audit log was no help for timing: events took over an hour to become searchable, timestamps are UTC, and what did appear was provisioning and list views, not a "transcript added" event.

  Select CreationDate, UserIds, Operations | Sort CreationDate
# exact -ObjectIds matches on file URLs returned nothing (spaces, encoding, ingestion lag)

03Six layers, each blocking one thing

No single control does the job. The design only makes sense once you see which layer stops what.

04The build, in order

Every command here ran against a real tenant. Placeholders only; your values go in the angle brackets.

Site

New-SPOSite -Url "<site-url>" -Owner "<admin-upn>" -StorageQuota 10240 `
  -Title "<Site Title>" -Template "STS#3"     # team site, no Microsoft 365 group
# no output = success; provisioning takes a few minutes

$site = "<site-url>"
Set-SPOSite -Identity $site -SharingCapability Disabled
Set-SPOSite -Identity $site -DisableSharingForNonOwners
Set-SPOSite -Identity $site -RestrictContentOrgWideSearch $true   # Restricted Content Discovery
Get-SPOSite -Identity $site -Detailed | Select SharingCapability, RestrictContentOrgWideSearch

STS#3 means no Teams, no group mailbox, no group to sprawl. Three things surprised me here. The 10 GB quota came back as 26214400 — the tenant uses pooled storage (StorageQuotaAllocated = 0), so per-site quotas are ignored; leave it, because switching is tenant-wide. DisableSharingForNonOwnersStatus often reads blank, so confirm in the UI (Settings › Site permissions › Change how members can share: Only site owners can share, and Allow access requests: Off). And Restricted Content Discovery needs SharePoint Advanced Management, which comes free once the tenant has a single Microsoft 365 Copilot licence assigned. The site header then shows a Restricted badge.

Access group — and why it has to be mail-enabled

Connect-ExchangeOnline
New-DistributionGroup -Name "<sg-name>" -Type Security -PrimarySmtpAddress "<sg-mail>" `
  -ManagedBy "<owner-upn>" -Members "<owner-upn>" `
  -MemberJoinRestriction Closed -MemberDepartRestriction Closed
Set-DistributionGroup "<sg-name>" -HiddenFromAddressListsEnabled $true
# expect: Universal, SecurityEnabled · ManagedBy = owner · Closed/Closed · hidden · RequireSenderAuthenticationEnabled True

Label encryption grants rights to an email address. A plain Entra security group has none, so it can't appear in the label. A mail-enabled security group works for the label and SharePoint permissions. Two side effects: membership is managed in Exchange (EAC or Add-DistributionGroupMember) — Entra won't let you edit it — and ManagedBy lets the business owner approve members from Outlook.

Connect-SPOService -Url "https://<tenant>-admin.sharepoint.com"
Set-SPOUser -Site $site -LoginName "<owner-upn>" -IsSiteCollectionAdmin $true
Get-SPOSiteGroup -Site $site | Select Title
Add-SPOUser -Site $site -LoginName "<sg-mail>" -Group "<Site Title> Members"
# "user not found" = group hasn't synced to Entra yet; wait 5-15 min

Members (edit), not Visitors: generating a transcript manually needs edit rights. Hold on to that fact — it comes back to bite in section 05.

Personal devices

Check the starting state, and check the owner's laptop is actually compliant — otherwise you lock out the person you're building it for:

Get-SPOTenant | Select ConditionalAccessPolicy                         # must stay AllowFullAccess
Get-SPOSite -Identity $site -Detailed | Select ConditionalAccessPolicy

Connect-MgGraph -Scopes "DeviceManagementManagedDevices.Read.All"
Get-MgDeviceManagementManagedDevice -Filter "userPrincipalName eq '<upn>'" |
  Select DeviceName, ComplianceState, JoinType, ManagementAgent, OperatingSystem
# ComplianceState compliant is what counts; a blank JoinType is fine

Then one Conditional Access policy: users = the group only; target = Office 365 SharePoint Online (not "Office 365"); no conditions, no grant; session = Use app enforced restrictions; On. Ignore the portal nudges to target Office 365 and the warning that SharePoint "will also affect Teams, Planner…" — app-enforced restrictions only bite on sites that ask for them. Finally the site setting, covered properly in the next section.

Sensitivity label

With none, turning on EnableAIPIntegration changes nothing users can see — that was the argument for treating it as a prerequisite of the approved change rather than a new approval. New-Label may print "WARNING: Encountered WebException while getting UDP policy"; it's harmless. And without -IncludeDetailedLabelActions every encryption field reads blank, which looks exactly like the settings didn't save.

Expect Enforce, both locations, an empty Settings, and DistributionStatus Pending for about an hour (up to 24) before Success. The label actually appeared in SharePoint's menu before the status flipped. "WARNING: Force Validate not set" is informational.

Library default label, never a policy default label

A policy-level default would stamp this label on every new document those users create anywhere — memos, emails, their own work — and encrypt it to one group with no copy or print. The library default (Documents › Library settings › Default sensitivity labels) labels only what's saved in that library. Add the Sensitivity column to the view while you're there.

If you ever open a PowerShell-built label in the Purview portal to check it, the mapping is: Control access = encryption on; Assign permissions now = Template; User access expires: Never; Allow offline access: Never = 0 days; and under Assign permissions › Custom, View content, View rights, Edit content, Save and Allow macros ticked, with Copy and extract, Print and Export unticked. Then press Cancel — re-saving through the wizard can normalise settings you set in PowerShell.

05Personal devices: browser-only wasn't enough

The approved design said "browser-only, no downloads." Testing it showed exactly what that does and doesn't mean.

The CA policy doesn't block anything itself. For users in its scope, it tells SharePoint the device's state and asks SharePoint to enforce its own restriction. SharePoint then applies whatever the site says — so every other site, still at the tenant's AllowFullAccess, carries on as before:

Site settingUnmanaged device gets
AllowFullAccessEverything
AllowLimitedAccessWeb only. No download, print or sync (Microsoft's fixed definition)
BlockAccessNothing

I tested limited access with my test account in the group, a fresh InPrivate window on a non-client laptop:

  • ✔Banner: "Your organization doesn't allow you to download, print, or sync using this device…"
  • ✔Download gone from the toolbar, the file menu and the More submenu. Sync gone.
  • ✔Transcript download greyed out: "You don't have permission to download the transcript."
  • ✔Word files open in "View mode – Edits can't be made" once AllowEditing $false is set.
  • ✘Transcript lines still editable, video still trimmable — in the same session.
  • ✘Transcript text still copyable out of the browser.
Set-SPOSite -Identity $site -ConditionalAccessPolicy AllowLimitedAccess
Set-SPOSite -Identity $site -AllowEditing $false     # prompts to (re)set AllowLimitedAccess: Y
Get-SPOSite -Identity $site -Detailed | Select ConditionalAccessPolicy, AllowEditing, LimitedAccessFileType
# keep LimitedAccessFileType = WebPreviewableFiles — OfficeOnlineFilesOnly stops video preview

AllowEditing covers Office files in Office for the web. It does nothing in the Stream player, where editing follows site permissions — and site permissions have to be edit, because generating a transcript needs edit. There is no Microsoft setting that makes the video player read-only on some devices and editable on others.

So the site moved to BlockAccess: personal devices get "You can't access this site — Due to organizational policies, you can't access this resource from this untrusted device," every other site still opens from the same session, and the sign-in log shows the CA policy as Success with session control "Use app-enforced restrictions." Two quirks: switching to BlockAccess silently resets AllowEditing to True (no effect while blocked; set it again if you ever go back), and anyone outside the CA policy's scope — including the admin who built it — isn't subject to the device rule at all.

A compliant laptop can still look "unmanaged"

InPrivate windows and browsers without the work identity don't pass device state. Edge signed in with the work profile does; Chrome needs the Microsoft Single Sign On extension. Put that in the user guide, or the first person working from a perfectly good laptop will report the site as broken.

06The detour: Defender for Cloud Apps

The one product that can block copy, paste and print inside the browser. It worked. It just couldn't be pointed at one site.

Session control routes the browser through a reverse proxy. I scoped a test CA policy to my account only (Office 365 SharePoint Online, client apps = Browser, session = Use Conditional Access App Control › Use custom policy), then built a session policy in the Defender portal (Cloud Apps › Policies › Policy management › Conditional Access tab):

  • Before the first routed sign-in, Defender says "You don't have any apps deployed with Conditional Access App Control." Sign in once through the policy and SharePoint appears under Automatic Entra ID onboarding.
  • Session control type: Block activities. Device tag does not equal Intune compliant / Hybrid joined. App = Office 365 SharePoint Online.
  • Activity types available for SharePoint: Cut/Copy item, Paste item, Print. That's the whole list. None of the templates mention editing either.
  • Filters available: activity type, app, device, IP address, location, registered ISP, user, user agent string, user agent tag. No site, URL or sensitivity label.

The behaviour was clean: the address bar became <tenant>.sharepoint.com.mcas.ms after a "monitored" notice; Edge offered to "Switch to work profile" (I chose Continue with current profile, so no client account landed in my browser); the first page was the tenant's root site rather than the link I'd asked for. Then: copy blocked with my custom message, paste blocked, print rendered as "Print Restricted – This page cannot be printed" — and typing an edit into a transcript line, or trimming the video, still worked. Video playback and the transcript pane behaved normally through the proxy.

Without a site filter, rolling it out would block copy and print for those users across all of SharePoint and OneDrive, and proxy all of it. That's a defensible policy for some organisations, but it isn't "protect this site." The test policies went off, and it's documented as its own use case for the day someone wants exactly that.

A few rules that confused people more than once, so they're worth stating flatly:

To…You need
See a label already on a fileOnly access to the file
Apply or change a labelTo be in the label policy
Remove or downgrade an encrypting labelExport or Full control on that file — the person who applied it, or a SharePoint admin with Unlock-SPOSensitivityLabelEncryptedFile (audited, with a justification)
Open a labelled Word/PDFMembership of the group the label grants rights to, or ownership of the file

Being a SharePoint site owner adds nothing inside an encrypted file. Site permissions and label rights are separate systems that happen to meet in the same library.

Myth

"Documents are labelled automatically" means every file in the library.

Reality

Office and PDF only. MP4s can't be labelled automatically or by default — only by a person (a Teams recording can inherit a meeting label; uploads can't). Audio files can't be labelled at all.

Myth

Restricted Content Discovery keeps Copilot away from the site.

Reality

It keeps the content out of general Copilot and search results. A licensed user who can open a file can still use Copilot on it. The label without EXTRACT is what actually closes that.

08Copilot: what a licence adds, and the questions to ask

Someone always asks. Here's the sourced answer.

  • Word Transcribe goes from 300 to 30,000 minutes a month. Nothing else about it changes, including where the audio is stored.
  • Copilot in Stream summarises a video, answers questions and finds where topics come up. It needs an existing transcript and permission to view the video. It doesn't create transcripts.
  • Enterprise data protection applies (Data Protection Addendum and Product Terms): prompts, responses and data reached through Graph aren't used to train foundation models.
  • Copilot returns anything the user can see. Oversharing is the risk, not the model.
  • Web grounding sends queries to Bing under the Microsoft Services Agreement, with Microsoft as an independent controller. Admins can switch it off for people handling sensitive material.
  • Prompts and responses are stored in the tenant for audit and eDiscovery — a records-management question for investigative content.
  • Check who's actually licensed. With group-based licensing, the licensing group's membership is the control point. In this tenant one person held a licence and nobody in the access group did.

09"Unlimited retention" — check before you promise it

The client's answer was "unlimited." That can mean two very different things.

Get-RetentionCompliancePolicy | Select Name, Enabled, Mode, @{n='SharePoint';e={$_.SharePointLocation -join ', '}}
Get-RetentionComplianceRule   | Select Name, Policy, RetentionDuration, RetentionComplianceAction
Get-ComplianceTag             | Select Name, RetentionAction, RetentionDuration, RetentionType
Get-SPOTenant | Select EnableAutoExpirationVersionTrim, MajorVersionLimit, ExpireVersionsAfterDays
# here: three empty results, then  False  500  0  (site inherits)

No delete policies, no retention labels, 500 versions kept with no expiry. So "kept until someone deletes it" was already true — no build needed — and every transcript edit stays in version history. The flip side: nothing prevents deletion, and a deleted file is recoverable for up to 93 days, then gone. A "retain forever" policy would protect everything, but it's close to irreversible and storage only grows. That's a decision to put back to the client in those words, not one to make for them. (Check Site lifecycle management policies in the SharePoint admin center too.)

10Go-live: three surprises in the first two files

Testing was done with my files. Real use is done with theirs.

The first file was audio. The request had said MP4. The first upload was an .m4a, and it just sat there: no transcript, no Generate option. Stream transcribes video formats only — mts, m2ts, ts, 3g2, 3gp, 3gp2, 3gpp, asf, wmv, avi, m4v, mov, mp4, mp4v, ogg, webm, movie, mkv, mpg, mpeg. Audio files also can't carry the label. The fix is always on a working copy, so the original stays untouched as the record:

  • In the library, "…" › Copy to (same library), then rename the copy from .m4a to .mp4 and accept the extension warning. Both are MPEG-4 containers, so this usually works — but I haven't confirmed it yet, so test it on something non-sensitive first.
  • Or make a real video from the audio, on a managed machine:
ffmpeg -loop 1 -f lavfi -i color=c=black:s=640x360 -i "input.m4a" `
  -c:v libx264 -tune stillimage -c:a copy -shortest "output.mp4"
  • Or use Word Transcribe for that one file — it takes .m4a and separates speakers — accepting that the audio lands in the user's OneDrive.

The second file showed "No label." It transcribed fine. Two different people asked why the label "didn't apply," and the answer both times was that nobody had applied it — MP4s are manual, always. Before anyone labels it, everyone sees "No label."

The transcripts had to go somewhere else. The team needed the text in a separate case-management and reporting system, readable by colleagues outside the access group. A labelled transcript opens only for the group — so neither those colleagues nor, quite possibly, that system could read it. The guidance became an order of operations:

  1. Open the video › Transcript › Download, and put that copy straight into the other system. Don't save it back into the library first (the library would label it).
  2. Only then label the video, if it shouldn't be downloadable — the label also disables transcript download.
  3. Once it's in the other system, that system's access controls apply, not the site's.

Step 1 rests on one assumption I haven't verified yet: that a transcript downloaded from an unlabelled video comes out unlabelled. It should, because it never touched the library — but "should" isn't "tested," and I've told them so.

Smaller things from the first week: a (1) on a file name meant a double upload. A colleague outside the access group managed to open a real recording, which earns a quick access review — and a reminder that support staff confirm a transcript exists and stop there:

Get-SPOUser -Site $site -Limit All | Select DisplayName, LoginName, IsSiteAdmin, Groups | Format-Table -AutoSize

And before adding anyone new, check their laptop is compliant. With BlockAccess on, a non-compliant device gets "You can't access this site," and that reads as broken, not secure.

13Rollback and handover

# rollback
Set-SPOSite -Identity $site -ConditionalAccessPolicy AllowFullAccess       # device rule off
Set-SPOSite -Identity $site -RestrictContentOrgWideSearch $false
Remove-LabelPolicy "<policy>"            # label stops appearing; labels already on files stay
Unlock-SPOSensitivityLabelEncryptedFile -FileUrl "<file-url>" -JustificationText "<reason>"
# CA policy: Off, then delete.  EnableAIPIntegration $false once labels are in use = mixed state; avoid

# handover — primary owner first, or you can't remove yourself
Set-SPOSite -Identity $site -Owner "<owner-upn>"
Set-SPOUser -Site $site -LoginName "<admin-upn>" -IsSiteCollectionAdmin $false
Remove-SPOUser -Site $site -LoginName "<admin-upn>" -Group "<Site Title> Owners"
Set-LabelPolicy "<policy>" -RemoveExchangeLocation "<admin-upn>"
Remove-DistributionGroupMember "<sg-name>" -Member "<admin-upn>" -Confirm:$false

The build account has to come off the site precisely because it sits outside the CA policy's scope — it's the one account the device rule never applied to. Delete the test files, turn off test policies, and send a one-page guide: upload from a work laptop; video only; download the transcript before labelling; label anything that mustn't leave; turn off comments and reactions; check the transcript against the recording; Edge signed in with the work profile.

Two findings came out of the work that weren't part of it, and I raised them separately: the tenant's default external sharing allowed "Anyone" links (this site overrides it; others may not), and Copilot's licensing group needs watching whenever access-group membership changes.

The one-line model

Stream keeps the transcript with the video; the site, the group and a site-level device rule keep the video in place; an encrypting label without EXTRACT keeps documents protected after they leave and keeps Copilot out. None of them can make the video player read-only on a personal device, label an MP4 for you, or transcribe an audio file — so test with your files, then expect the client's files to be different.
