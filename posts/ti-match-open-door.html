Field case · Threat-intel alerts & exposure

The TI match was the least interesting part

Two threat-intel alerts fired on firewall syslog. One was Cloudflare noise. The other led to an email archiver whose admin page had been reachable from the whole internet, held open by a firewall rule nobody remembered was there for mail journaling.

Ram Mudigina November 16, 2026 ~10 min read
  • Alerts: two hits on Sentinel's TI match for an IP in Syslog rule, same firewall, a few hours apart.
  • One: a Cloudflare edge address pulling content from a site behind Cloudflare. False positive.
  • The other: an IP tagged to an emerging threat cluster held sessions open on an email archiver's admin port, through a 1:1 NAT that allowed any port from anywhere.
  • Why the rule existed: Exchange Online journaling delivers to the archiver on port 25. Nobody had scoped it to just that.
  • Fix: allowed inbound cut to TCP 25, validated from the outside and in message trace.

01What the rule actually tells you

A string appeared in a log line. That's all.

The analytics rule behind both alerts is one of the stock Sentinel threat-intelligence rules: take every active IP indicator, and look for it anywhere in SyslogMessage. When it matches, you get an incident with the indicator, its source (Microsoft's own feed here, confidence 83), and a threat-actor label.

What you don't get is everything you need for a verdict:

  • which direction the traffic went (inbound scan, or an internal machine calling out),
  • whether the firewall allowed or dropped it,
  • which internal host and port were involved.

So the incident is a pointer, not a finding. The verdict lives in the raw lines the firewall sent. Both alerts came from the same syslog source (the edge firewall's forwarder, which had sent 1.6 million lines in the past day), so the job was the same for both: find the lines, read them.

Syslog
| where TimeGenerated between (datetime(2026-11-10) .. datetime(2026-11-12))
| where SyslogMessage has_any ("<ioc-1>", "<ioc-2>")
| project TimeGenerated, HostIP, Facility, SyslogMessage
| order by TimeGenerated asc

02Alert one: Cloudflare, doing Cloudflare things

Shared edge addresses say almost nothing about who's behind them.

The first indicator sat in Cloudflare's address space, which thousands of customers share. Reputation services treat that block as a reverse-proxy range for exactly that reason. An indicator on one of those addresses is weak on its own.

The raw lines settled it. Five TCP/443 connections, within 0.4 seconds, on sequential source ports, to one public IP that a firewall rule published only on 443. That's what an origin pull looks like: Cloudflare's edge fetching content from a site it fronts. A DNS check confirmed the site on that public IP sits behind Cloudflare. Closed as a false positive.

03Alert two: the sessions that stayed open

An indicator with no public reporting, and traffic that was let through.

The second indicator was labelled with a Microsoft "Storm" designation, the name Microsoft gives an emerging or still-developing cluster of activity. Nothing public on the IP, nothing public on the cluster. That's not reassuring; it means you can't lean on anyone else's write-up.

The firewall here logs Meraki-style events, and the event type is the first thing to pull out of each line:

EventWhat it showed
ip_flow_startThree inbound sessions from the IOC to one of the organisation's public IPs: port 8000, then 443, then 443 again. Each NATed to the same internal host.
ip_flow_endA matching end for each, 4 to 5 minutes later. Held-open sessions, not dropped packets.
urlsThe internal host answering on 443 with the host name barracuda.barracudanetworks.com.

That last line identified the box. barracuda.barracudanetworks.com is the default certificate name on Barracuda appliances, and 8000 is the default port for their admin web interface. Asking the client confirmed it: their Barracuda Message Archiver, the appliance that keeps a copy of every email for compliance.

Widening the window found more. The same IP had visited a week earlier, before the indicator ever matched. The alert fired on the second visit, not the first.

Syslog
| where TimeGenerated > ago(30d)
| where SyslogMessage has_any ("<ioc-1>", "<ioc-2>")
| extend EventType = extract(@"\s(ip_flow_start|ip_flow_end|firewall|urls)\s", 1, SyslogMessage),
         Src    = extract(@"src=([\d\.]+)", 1, SyslogMessage),
         Dst    = extract(@"dst=([\d\.]+)", 1, SyslogMessage),
         DPort  = extract(@"dport=(\d+)", 1, SyslogMessage),
         NatDst = extract(@"translated_dst_ip=([\d\.]+)", 1, SyslogMessage)
| summarize Hits = count(), First = min(TimeGenerated), Last = max(TimeGenerated),
            Days = dcount(bin(TimeGenerated, 1d)) by Src, Dst, DPort, NatDst, EventType
| order by First asc

04The door: a 1:1 NAT with nothing on it

The firewall wasn't broken. It was doing exactly what it was told.

The archiver had a 1:1 NAT on the edge firewall: one public IP mapped straight to its internal address. The allowed-inbound rule on that mapping was any protocol, any port, from 0.0.0.0/0. Everything the appliance listened on, including the admin login page, was on the internet.

The timing made it worse. Eight days before the second visit, Barracuda had shipped patches for a command-injection flaw (CVE-2026-111560) that affects the Message Archiver among other products, with the fix released as BNMA-32468. An admin interface reachable from the internet is precisely the exposure that matters for that kind of bug. An IP tied to an emerging cluster holding sessions open on that interface, a week after the patch dropped, reads like reconnaissance.

The first job was confirming patch status. Barracuda support confirmed BNMA-32468 had been applied the day after release, so the specific bug was closed before either visit. The exposure still had to go.

"It's internal only" is a claim. Test it from outside.

The first answer from the client side was that the archiver was private and not reachable from the internet. It was a reasonable belief: they reached it on its internal address over VPN. A test from an outside network loaded the login page in seconds. Believe the log line, then prove it from the attacker's side.

05Why the door was there: journaling

You can't close a rule until you know what's walking through it.

The obvious fix was to remove the NAT. The obvious fix would have broken compliance archiving. The archiver gets its copies of email through Exchange Online journaling:

  1. A journal rule in Exchange Online says "for every message, send a journal report to this address".
  2. The address lives on the archiver's own domain, so an outbound connector routes it to a smart host.
  3. The smart host is the archiver's public IP, and the delivery is plain SMTP on port 25.

So Microsoft's mail servers on the internet genuinely needed to reach that appliance, on one port. Somewhere along the way the rule had been written as "allow everything" instead of "allow 25", and it stayed that way because it worked.

Get-JournalRule | Format-List Name, Enabled, Scope, JournalEmailAddress
Get-OutboundConnector | Format-List Name, Enabled, SmartHosts, RecipientDomains

# then prove reports are actually flowing, before and after any change
Get-MessageTraceV2 -RecipientAddress "journal@<archiver-domain>" -StartDate (Get-Date).AddHours(-2) -EndDate (Get-Date) |
  Select-Object Received, SenderAddress, Status | Sort-Object Received -Descending | Select-Object -First 20

Not every allowed connection is a "flow"

My first pass at "does Microsoft even reach this box?" only looked at ip_flow_start events and found nothing, which suggested port 25 wasn't needed. Wrong. The journaling deliveries were logged only as firewall events. Query every event type before concluding traffic doesn't exist.

06The change, and proving it

Collect the before, make one change, collect the after.

The change went through the client's change process with sign-off from both sides: on the archiver's 1:1 NAT, allowed inbound changed from any / any / 0.0.0.0/0 to TCP 25. The source stayed open for now, because Exchange Online sends from a wide and changing set of addresses.

Before the change I captured the journal rule, the connector and a message trace of journal reports. Afterwards I checked the same things again, plus the attacker's view:

CheckBeforeAfter
TCP 8000 from the internetOpen, admin login pageClosed
TCP 443 from the internetOpen, admin login pageClosed
TCP 25 from the internetOpenOpen
Journal reports in message traceDeliveredDelivered
Admin access over VPN / internalWorksWorks

One more query to keep around: who else on the internet has been reaching that NAT target, and on which ports. It turns "the IOC visited" into "here's everyone who could".

Syslog
| where TimeGenerated > ago(14d)
| where SyslogMessage has "translated_dst_ip=<internal-ip>"
| extend EventType = extract(@"\s(ip_flow_start|firewall)\s", 1, SyslogMessage),
         Src   = extract(@"src=([\d\.]+)", 1, SyslogMessage),
         DPort = extract(@"dport=(\d+)", 1, SyslogMessage)
| where isnotempty(EventType)
| summarize Flows = count(), Sources = dcount(Src), TopSources = make_set(Src, 20) by DPort, EventType

07What's still on the list

Closing the door isn't the same as checking the room.

  • Review the archiver's admin and audit log for both visit windows: logins, failed logins, configuration changes.
  • Rotate the admin password. First check whether any scheduled report or script signs in with that account, or the rotation breaks it silently.
  • Scope TCP 25 to Exchange Online's published sending ranges instead of 0.0.0.0/0.
  • Block the IOC at the edge.
  • Re-run the exposure query after a week and confirm only port 25 traffic reaches the box.
  • Sweep every other 1:1 NAT on the firewall for the same "any / any" pattern.

Mental model

The TI match is a smoke alarm in the hallway. It tells you something burnt near a door. It can't tell you whether the door was locked. Only the raw log answers that, and here the door had been propped open for years for one delivery driver.

The one-line model

A threat-intel match tells you an IP appeared in a log. Read the raw lines to learn whether a door was open, and before you shut it, find out who still needs to walk through.
